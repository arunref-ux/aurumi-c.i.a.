## Architecture and integrity contracts

- New strengthened records use `aurumi.cia.delivery-content/2`; the released `/1` algorithm and all Phase 1–5 algorithms remain unchanged.
- Affected schemas explicitly distinguish `aurumi.cia.engagement-initiation/2`, `aurumi.cia.engagement-scope/2`, `aurumi.cia.engagement-review/2` and `aurumi.cia.engagement-completion/2`.
- The `/2` canonical seal covers every supplied immutable field except `integrityValue`, including the explicit marker, source identities, content, audit identity and nested evidence. Newly sealed objects exclude any preexisting integrity value before computing the new record's value. Historical immutable records are never resealed on restoration.
- Source obligations include original descriptions/criteria, mandatory/optional classification and source reference/value. Direct advisory criteria are explicit; where legacy caller input omits them, the explicitly authorized professional service commitments provide the fallback. Workstream/milestone linkage alone never satisfies a contractual artifact. Mapping records explicitly approve criterion coverage and bind referenced records; satisfaction requires current exact accepted versions containing the original criteria. Limited advisory services may use approved noncompletion review evidence instead.
- Initial scope IDs bind commencement; subsequent effective scope versions bind remaining/replacement obligations. Original obligations and approvals are retained. Amendments identify only their affected obligations and need independent approval.
- Completion material state includes original authorization, effective scopes, derived obligation state/mappings, required milestone/deliverable acceptance, all outcome definitions/baselines/observations/verification, concerns and explicit reviewed customer feedback/responsibilities. Prior reviews remain immutable and become stale by derived binding mismatch. Presentation and assignment acknowledgement metadata do not invalidate review.
- Outcome ownership/workstream authority is checked after awaits. Definitions/baselines/observations stay available after reassignment. Definition revisions create new versions; incompatible unit/type changes require a separate outcome. Baseline corrections require reason, evidence and approval. Observation supersession records original ID/reason and creates new unverified content.
- Verification binds measurement seal, pinned baseline seal, definition ID and decision/actor/time/evidence. Historical reviews embed exact outcomes and retain original measurement/definition/baseline references, independently validated against available history.
- Numeric domains cover duration/count/percentage/ratio/currency/signed/bounded/qualitative with unit, direction, bounds, integer and comparison semantics. Custom numeric domains need explicit comparison semantics. Strict timestamp validation rejects calendar rollovers, impossible times/offsets and actual future observations using normalized instants, while original timestamp text is retained.
- Noncommercial callers receive safe operational amendment terms; pricing/basis/impact, embedded revised proposal, commercial approval records, initiation/completion/scope canonical snapshots and review-state bindings are withheld. Canonical storage is deep-copied and never changed by projection. Redacted projections are not canonical sealed records. Arbitrary author-entered operational notes are not automatically redacted; no keyword/AI scanning claims are made.
- Every logically related mutation uses the existing acknowledged `store.durable`, including rollback/read-back and postawait canonical authorization/fingerprint checks. No new transaction framework, production infrastructure, authentication or permission authority was added.

- Unknown/malformed/stripped strengthened contracts fail closed. Invalid workspace/engagement relationships are quarantined with original payload; valid siblings survive. Failed quarantine-backup protection is preserved.
- Fault-injection tests confirm mapping, baseline, observation, verification, review, amendment, acceptance and completion never report success on failed persistence; reload/retry preserves prior committed state and avoids duplicate completed records/operations.
