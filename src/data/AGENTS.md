# Data layer rules
- Business Fit public services accept isolated bearer handles only; internal services recheck canonical prototype identity and feature/row permissions. Public pages omit the workspace shell; browser persistence is demonstrative, never production authentication or privacy.
- Business Fit new submissions use schema /2 and explicit `business-fit-submission-hash/1` canonical consistency over every immutable field except the value itself; markers fail closed. Sessions pin full compatible published questionnaire/rule/public-catalog copies and current evaluation uses only recursively effective responses. Genuine /1 history uses the frozen released evaluator, is never rewritten/upgraded, and needs an authorized source-bound review before new conversion; this is browser-local consistency, not cryptographic authentication.
- Business Fit material operations use `store.durable`: synchronous rollback on write/read-back failure, explicit attached persistence, and no completion without acknowledgment. Consultation persists stable session-bound intent before the mock ShopTalk await, persists the returned lead, then atomically commits all final relationships; retries reuse intent/key/reference, never another contact or source. Assessment conversion persists stable operation/source provenance and per-task progress; Assessment Studio's optional synchronous commit hook checks current canonical identity, authorization, lifecycle, assignment and source after every await, committing assessment plus recovery linkage together and completing intake only after all acknowledged imports. Ordinary Assessment Studio callers keep existing behavior, and imports remain self-reported/unverified, never approval.
- Business Fit definition publication and restoration check question/option references, operator types, visibility cycles, and compatible pairs; current connector claims require exact published/available catalog scope, direction, operations, system and active evidence, with controlled qualified wording. Related snapshot/consent/intake/operation/conversion identities are validated on restoration and downstream use, quarantining invalid work without deleting independent valid assessments or rewriting historical studios.
- Proposal Studio (`src/data/proposal-studio.ts`, hooks in `src/lib/proposal-queries.ts`) stores proposals in the shared `proposals` table with a pinned `source` solution hand-off (/2); such rows are blocked from generic repository updates, so lifecycle changes go only through the workflow service.
- Proposal deliverable classes, readiness and commercial totals are derived in `src/domain/proposal.ts` (never input); totals are per currency and billing period, taxes only when configured with a source, and prices are pinned references to the read-only Pricing Studio adapter, so a proposal can't become a competing price master.
- Submitting freezes a `proposalVersions` record whose content hash covers the whole embedded solution hand-off (assessment + catalog) and whose embedded identities must match the pinned source; approval and issue bind to that exact version and any later material edit supersedes it, so an old approval never authorizes changed terms. New versions declare `hashContract` /2; explicit markers never fall back (explicit /1 is unsupported). Only genuinely absent historical markers match the two released /1 and /2 algorithms independently: exactly one match plus all structural, financial and source checks is required. Derived runtime assurance metadata never rewrites history, and all unmarked versions remain blocked from fresh approval/issuance. This is compatibility/consistency, not cryptographic authentication of browser storage.
- Proposal sharing and recipient responses are simulated records (`proposalShares`); acceptance is never treated as a signed contract.
- Workflow decisions (submit, approve, issue, share) fingerprint the proposal before any adapter await and re-read, re-authorize and re-validate after it, committing synchronously, so a decision never lands on state that changed while it waited.
- On line updates an omitted `catalogItemId` keeps the stored capability (null may never remove an existing binding), so a new price never silently re-labels the product. Published prices bind to a line's `catalogItemId` and are valid only through `validUntil` (proposalClock; calendar-checked, never Date.parse alone); mismatches or expiry need a separately authorized `priceException`, and stored versions are re-verified (amounts, totals, hash) on reload and before approval/issue.
